# تجربة FRESH على Odoo Community

الحالة في 2026-09-24: تعمل حاويات Odoo Community 19 وPostgreSQL محليًا. أُنشئت قاعدة `fresh_trial` وتحقق تسجيل دخول المدير عبر API وتثبيت `point_of_sale` وظهور صفحة الدخول في المتصفح. أُنشئ كاشير `FRESH — Trial Cashier` وثلاثة أصناف تجريبية بلا ضريبة بأسعار وهمية بالليرة. لم تُختبر دورة البيع والطباعة والأوفلاين بعد، ولم تُستورد بيانات المحل أو تُنفذ تخصيصاته.

## التشغيل المحلي

يتطلب Docker Desktop يعمل مع Linux containers. من داخل هذا المجلد:

```sh
python3 prepare.py
docker compose up -d
```

افتح http://localhost:18069 وسجّل الدخول باسم `fresh.admin`. كلمة المرور محفوظة في `secrets/trial_login.json`، ولا تنشر هذا الملف. قاعدة `fresh_trial` موجودة بالفعل وبلد الشركة لبنان. كلمة إدارة قواعد البيانات منفصلة وهي قيمة `admin_passwd` في `config/odoo.conf`. لا تثبّت تطبيقات تتطلب Enterprise أو خدمات مدفوعة.

لإعادة تجهيز بيئة تجربة جديدة فقط: `python3 bootstrap_trial.py` ثم `python3 seed_trial.py`. السكربتات تستعمل API المحلي وتنشئ البيانات التجريبية الناقصة. المنفذ 18069 اختير لأن بيئة أخرى على الجهاز تستخدم 8069؛ لم تُعدّل تلك البيئة.

الإعداد محلي فقط ولا يفتح منفذ قاعدة البيانات. الملفات الحساسة مستثناة من Git. ملف إعداد Odoo قابل للقراءة محليًا ليستطيع مستخدم الحاوية قراءته؛ هذه بيئة تجربة على جهاز موثوق، وليست إعداد نشر نهائي.

```sh
docker compose ps
docker compose logs --tail=100 odoo
docker compose stop
```

البيانات محفوظة في volumes. لا تستخدم `down -v` لأنه يحذف بيانات التجربة. وجود volumes ليس نسخة احتياطية؛ يلزم اختبار نسخ قاعدة البيانات وملفات المرفقات واسترجاعهما قبل التشغيل الفعلي.

## نطاق النسخة المطلوبة

### ترتيب شاشة المرجع

تمت إضافة `register_layout.xml` و`register_layout.scss`: على الشاشات بعرض 768px فأكثر يظهر جدول المبيعات يسارًا، والأقسام والأصناف تحته، وحقل باركود والكيبّاد 7–8–9 والإجمالي التركوازي والدفع السريع يمينًا. الجدول مرتبط بخطوط Odoo الأصلية واختيارها وتعديلها، وليس معاينة ثابتة. يبقى العرض الأصلي المتكيف على الشاشات الصغيرة. زر الطباعة يبدّل إعداد الطباعة في جلسة الواجهة الحالية؛ لا يحفظ سياسة طباعة دائمة للخادم. عندما تتوقف الطباعة يبقى مسار إيصال Odoo العادي.

تمت المراجعة البصرية عند 1280×900 و1024×768، واختبار إضافة مياه، تعديل الكمية إلى 2 من الكيبّاد ثم Enter، وإتمام بيعة Whish بمبلغ 100,000 ل.ل من الأزرار الموجودة يمينًا. اختصارات Enter للانتقال بين الكمية والسعر حسب الطلب الأصلي لم تنفذ بعد؛ زر Enter الحالي يثبت الإدخال. عرض مقابل الدولار ينتظر تنفيذ العملتين وسعر الصرف.

### الدفع السريع المنفذ في 2026-09-25

إضافة `addons/fresh_pos` مثبتة. افتح `http://localhost:18069/pos/ui/2` للكاشير **FRESH — Quick Checkout**. الكاشير الأول بقي كما هو لأن عليه جلسة مفتوحة وبيعة سابقة. تُضبط طرق الدفع بواسطة `configure_quick_checkout.py` قبل فتح الجلسة، ولا يعاد تشغيله أثناء وجود جلسة مفتوحة.

ثلاثة أزرار متجاورة: كاش / Cash، ويش / Whish، توترز / Toters. كل زر يسجل المبلغ الكامل عبر مسار Odoo الأصلي، ويطلب الطباعة التلقائية ثم ينتقل لفاتورة جديدة. الدفع التفصيلي متاح للمبالغ الجزئية والباقي. ويش وتوترز تسجيل للتحصيل فقط، ولا يتصلان بمزود دفع. أضيف قفل لمنع الضغط المتزامن، والطلبات ذات الدفعات الموجودة والمرتجعات تذهب لشاشة الدفع العادية. هذا لا ينفذ موافقات المدير للمرتجعات بعد.

اختبار فعلي عبر الواجهة وقاعدة البيانات: Cash بقيمة 50,000 ل.ل، Whish بقيمة 100,000، Toters بقيمة 75,000. كل عملية محفوظة `paid` ولها دفعة واحدة بالطريقة والمبلغ الصحيحين. Toters اختُبرت بالضغط المزدوج ولم تتكرر العملية. ظهر اسم الطريقة في إيصال Whish وToters، وتم رصد العودة لسلة جديدة بعد Whish. سجل Odoo طلب طباعة واحدًا لكل عملية؛ لم تُختبر طابعة USB أو الجارور أو الطباعة الصامتة. المتصفح العادي قد يحتاج نافذة طباعة؛ الربط المباشر بالطابعة يحتاج تجهيزًا إضافيًا على ويندوز.

باقي المتطلبات أدناه لم تُنفذ بالكامل، خصوصًا العملتين والصرف، صلاحيات وموافقات المدير، الديون وبوابة الزبائن، إقفال اليوم المخصص، المزامنة واستقلال الكاشير عند تعطل الخادم.

- أكثر من ثلاثة كاشيرات، فروع لاحقًا، وشاشة Check Price مستقلة.
- واجهة عربي/إنجليزي حسب صورة المستخدم: السلة يسارًا والكيبّاد يمينًا، باركود، أقسام، أصناف بلا باركود واختصارات.
- دولار ولبناني، سعر صرف يديره المالك، بلا TVA، دفع Cash / Whish / Toters مع بيان الطريقة على الإيصال.
- PIN للموظفين وصلاحيات مالك ومدير وكاشير ومحاسب. تغيير السعر بإذن لكل موظف وسجل تدقيق.
- موافقات مدير للمرتجع والخصم، إشعارات عند الاتصال وموافقة محلية أثناء الانقطاع.
- Cash on Hand لكل موظف، عهدة ثابتة، تسليم الزيادة مع تأكيد المستلم. End of Day مستقل عن منتصف الليل وعن طباعة الإيصال.
- كاشير خارجي بمبيعات فعلية، والتحصيل بعهدته حتى تسليمه للمحل.
- حسابات زبائن بسقف دين، دفعات جزئية وتفاصيل المشتريات. لا أرصدة افتتاحية قديمة.
- صفحة خاصة للزبون مع وقت آخر تحديث. المستخدم يريد دخولًا بالرقم فقط؛ هل الرقم هاتف أم رمز سري لم يُحسم. لا تنشر بيانات مالية برقم هاتف عام وحده.
- تصوير فاتورة المورد، استخراج الاسم والمبلغ، مراجعة واعتماد، دفع كامل/جزئي/آجل ومصدر الدفع.
- المخزون غير مفروض عند الانطلاق. الاحتفاظ بمعرفات المنتجات والتصنيفات والصور لتطبيق طلبات لاحق.
- مراقبة سلة الكاشير داخل التطبيق، وتقارير المبيعات والمصاريف والموردين والصناديق والتصدير.

## أسئلة معلقة

- مصدر بضاعة الكاشير الخارجي ومكان تسليمها.
- نموذج الطابعة الحرارية USB وعرض الورق، واختبار العربية والدرج على ويندوز.
- آلية دخول الزبون بالرقم، ومتطلبات المحاسب التفصيلية.
- ملف المنتجات الأصلي غير متاح الآن. لا تعتمد أسعارًا أو باركودات غير موثوقة من `../import.csv`.

## شروط قبول التجربة

جميع البنود التالية **لم تُختبر**:

1. فتح ثلاث جلسات كاشير مستقلة وعدم اختلاط السلال أو الصناديق.
2. بيع تجريبي نقدي، Whish، Toters، ومرتجع مرتبط بالأصل.
3. اختبار USD/LBP والدفع المختلط والباقي والتقريب، وحفظ سعر الصرف للعملية بعد تغييره لاحقًا. لا تفترض دعمًا جاهزًا داخل POS.
4. فصل الاتصال عن كاشير، تنفيذ عدة مبيعات، إعادة الاتصال والتأكد من مزامنة كل عملية مرة واحدة.
5. إعادة تحميل المتصفح وإغلاقه وإعادة تشغيل الجهاز أثناء الانقطاع. توثيق Odoo يحذر من ذلك؛ لا تعتبر الاستقلال الكامل متاحًا قبل اختبار وتطوير معالجة موثوقة.
6. تعطل السيرفر المحلي واختبار استرجاع المبيعات. خادم محلي وUPS وحدهما لا يحققان استقلال الكاشير.
7. منع تجاوز سقف الدين أثناء الاتصال؛ عند الانقطاع موافقة مدير مع إظهار أن الرصيد قديم. لا ضمان لسقف إجمالي بين أجهزة منفصلة دون تخصيص حد محلي أو حظر البيع بالدين.
8. تسليم وردية وتأكيد استلام النقد وتسجيل الفرق، ثم إقفال يوم يمتد بعد منتصف الليل.
9. طباعة عربي/إنجليزي وفتح الدرج على الأجهزة الحقيقية، وفشل الطباعة لا يكرر عملية البيع.
10. حساب زبون لا يمكنه الوصول لحساب غيره، وصلاحيات الموظفين مفروضة في الخادم.

## الاستضافة

القرار المعتمد: السيرفر التشغيلي داخل المحل على جهاز دائم التشغيل مع UPS. يوصل الراوتر والسويتش أيضًا بمصدر احتياطي. تم إلغاء اقتراح QNAP والمكتب البعيد. تتصل الكاشيرات بسيرفر المحل عبر الشبكة المحلية؛ انقطاع الإنترنت وحده لا يقطع هذا الاتصال. تعطل السيرفر أو الشبكة المحلية يحتاج معالجة منفصلة، ولا توجد حاليًا آلية مستقلة منفذة لكل كاشير.

إعداد Compose الحالي مخصص للتجربة على جهاز التطوير ويستمع على localhost فقط، وليس إعداد شبكة المحل النهائي. الوصول الخارجي للكاشير والزبائن والداشبورد يحتاج تصميم اتصال آمن واختبارًا قبل نشره. لا تفترض إتاحة الخادم المحلي من الإنترنت.

هذه التجربة لا تستخدم Enterprise ولا تنشر على الإنترنت. Odoo يحتاج خادم تطبيق وPostgreSQL؛ Vercel ليس بديلًا مباشرًا له. يمكن استخدام Vercel لبوابة مستقلة مستقبلًا. دور Supabase لم يُحسم، ولا توجد مزامنة سحابية منفذة. لا تستخدم قاعدتين كمصدرين مستقلين للأرصدة المالية.
